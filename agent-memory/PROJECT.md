# Durable Project Memory

## Product mission

Build and operate fast, trustworthy property websites that help a prospective
guest understand a stay and make a qualified booking enquiry with confidence.
The product is a reusable static-site engine plus a clean seed for new
properties, not a one-off page that is copied between customers.

## Current product model

- The root folder is a configured example implementation. `property-2/` is a
  second example implementation.
- `template/` is the canonical clean seed. It deliberately contains no live
  customer, contact, booking, analytics or SEO information.
- A property-specific site keeps its content and options in `site-data.js`.
- The reusable frontend engine is plain HTML, CSS and JavaScript; there is no
  package build step.
- The site supports English and Thai property content plus shared UI strings.
- Booking is an enquiry workflow with manually maintained blocked dates. Live
  channel synchronisation is future work, not current behaviour.
- Netlify hosts the static site. `DEPLOYMENT.md` is the release runbook.

## Directory map

| Location | Purpose |
| --- | --- |
| `template/` | Clean starting point for new property repositories |
| `site-data.js` | Property facts, media references, SEO, booking and optional tracking configuration |
| `script.js`, `booking-logic.js`, `translations.js`, `style.css` | Shared website engine and presentation |
| `schema/`, `scripts/`, `tests/` | Validation, SEO generation and automated checks |
| `PROPERTY-INTAKE-BRIEF.md` | Client fact-gathering workflow |
| `PROPERTY-CHECKLIST.md` | Property configuration checklist |
| `DEPLOYMENT.md` | Netlify and go-live workflow |

## Durable rules

1. Begin each customer site from `template/`, not from an existing configured
   property.
2. Keep customer data isolated. Never reuse identifiers, endpoints, contact
   information, images or search verification values across properties.
3. Edit configuration before editing the shared engine. Change the engine only
   when the capability benefits the reusable product.
4. Run schema validation, SEO synchronisation and automated tests before
   release whenever property configuration changes.
5. A browser smoke test is mandatory for an interactive, layout or launch
   change. Booking must be tested as the guest experiences it.
6. `agent-memory/` contains process knowledge and decisions only; it never
   stores credentials, personal information or copied customer configuration.

## Known architectural limits

- The static site has no server-side booking inventory or payment processing.
- Availability dates are manually managed until a verified integration exists.
- Social and search crawlers need static metadata generated by
  `scripts/sync-seo.js`; client-side JavaScript alone is insufficient for that
  job.
- Any new third-party tool must be judged for maintenance burden, privacy,
  customer ownership and a safe fallback when it is unavailable.

## Evidence and validation commands

```text
node scripts/validate-config.js
node scripts/sync-seo.js
node --test
```

After the commands pass, use a local browser to review the changed journey at
mobile and desktop sizes. Refer to `AGENTS.md` for the full quality gate.

## Product questions not yet decided

- Which types of properties and countries are the next target market?
- Is the primary commercial model bespoke site delivery, a productised service,
  or a self-serve subscription?
- What guest/owner dashboard or calendar integration, if any, deserves to be
  the next reusable capability?

Do not answer these by silently coding. Use the product strategist role to
frame a hypothesis and obtain the owner's direction before a material build.
